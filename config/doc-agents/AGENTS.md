## 文档仓规范（DevFlow 代码生成流水线）

本仓库是**文档仓**，与**代码仓**分工不同：

- 代码仓：存放可运行的代码、构建脚本与产物，由流水线自动修改、编译、提交。
- 文档仓：存放知识、方案、经验、流程、技能与规则，供人与 AI 阅读；流水线从方案仓读取需求。

不要把可运行代码放进文档仓；也不要把方案正文散落到代码仓。

### 几个目录的区别与归档位置

| 目录 | 定位 | 放什么 | 不放什么 |
| --- | --- | --- | --- |
| `docs/version/` | 方案仓 | 每个 US 一个文件夹的完整方案，流水线据此开发 | 长期知识、踩坑复盘 |
| `docs/knowledge/` | 知识库 | 长期稳定的领域知识、术语、模型、背景 | 单个需求的方案 |
| `docs/memory/` | 经验库 | 已发生的踩坑、根因、解决方案与预防 | 稳定知识、通用流程 |
| `docs/learn/` | 工作流 | 团队研发/评审/发布/排障等流程规范 | 需求方案、一次性的复盘 |
| `skills/` | 技能仓库 | 可复用的能力说明与可执行步骤 | 背景知识、硬性规则 |
| `docs/rules/` | 规则仓库 | 必须遵守、尽量可自动检查的约束 | 流程叙述、经验记录 |

归档判断：

1. 需求、方案、验收 → `docs/version/`。
2. 长期有效的事实与术语 → `docs/knowledge/`。
3. 踩坑与复盘 → `docs/memory/`。
4. 做事步骤与协作流程 → `docs/learn/`。
5. 可被重复调用的能力 → `skills/`。
6. 不能违反的硬性约束 → `docs/rules/`。

拿不准时优先放知识库或经验库，并在文档里链接到对应方案；不要新建平行目录。

### 方案文档规范

所有方案统一放在 `docs/version/` 下，一个方案一个文件夹，不要把多个方案混在一起，也不要放到其他目录。

- 目录：`docs/version/<方案编号>-<日期>-<方案名称>/`
- 命名格式：`方案编号-日期-方案名称`
  - 方案编号：`US` + 6 位数字，例如 `US000001`
  - 日期：`YYYYMMDD`，例如 `20260315`
  - 方案名称：简短中文或英文，不能包含 `/ \ : * ? " < > |`
- 示例：`docs/version/US000001-20260315-增加一个用户管理系统/`

方案文件夹内按以下顺序编写，缺少的章节要显式写「无」并说明原因：

| 文件 | 内容要求 |
| --- | --- |
| `README.md` | 方案概览、目录说明、变更历史 |
| `01-需求分析.md` | 背景、目标、范围、验收标准 |
| `02-方案设计.md` | 总体架构、数据模型、接口设计、权限与安全、异常处理、风险与取舍 |
| `03-任务拆分.md` | 可执行任务、依赖关系、排期 |
| `04-验收清单.md` | 验收项、验收结果、回归范围 |
| `05-构建发布.md` | 构建、测试、打包命令（`test` / `build` / `package`），供流水线执行 |

### 特性编号与特性清单

同一特性可包含一个或多个方案，统一用「特性编号」登记，便于归档与检索：

- 清单文件：`docs/version/features.md`
- 表格列：`| 特性编号 | 方案目录 | 名称 | 说明 |`
  - 特性编号：`F` + 4 位数字，例如 `F0001`；
  - 方案目录：`docs/version/` 下的方案文件夹名，可填多个，用英文逗号分隔；
  - 名称/说明：给人阅读。
- 新增特性先在清单登记，再写方案文档；特性编号一经使用不要复用。
- 在应用内保存方案文档时，从该清单选择特性编号，文档会保存到对应方案目录。

示例：

| 特性编号 | 方案目录 | 名称 | 说明 |
| --- | --- | --- | --- |
| F0001 | US000001-20260315-增加一个用户管理系统 | 用户管理 | 账号、角色与权限管理 |

### 自动检测的硬性要求（流水线据此识别方案）

流水线按**目录位置 + 目录命名**自动识别方案。以下规则必须严格遵守，否则新方案不会被检测到，或被当成新方案重复开发：

1. 方案目录必须是 `docs/version/` 的**直接子目录**，不要再多套一层分类目录。
2. 目录名必须匹配 `^US\d{6}-(\d{8}|\d{4})-`（大小写不敏感）：
   - `US` + 6 位数字编号；
   - 用半角连字符 `-` 分隔（禁止全角「－」、空格、下划线）；
   - 日期用 `YYYYMMDD`（兼容旧的 `YYYY`）；
   - 示例：`US000001-20260315-增加一个用户管理系统`。
3. 一个 US 一个文件夹；编号与日期确定后不要改名，改名会被识别为新的 US。
4. 方案名称不要以 `US` 开头，也不要加额外前缀；不能包含 `/ \ : * ? " < > |`。
5. 自动检测只认默认目录（`docs/version`、`docs/knowledge`、`docs/memory`、`docs/learn`、`skills`、`docs/rules`）。若改用自定义目录，必须在「代码统计 → 代码生成流水线」里勾选并填写对应路径。
6. 代码生成依赖构建命令：`05-构建发布.md` 必须给出 `test` / `build`（`package` 可选）的命令代码块；也可用方案根目录的 `pipeline.json`（`{"test":"...","build":"...","package":"..."}`）或 `01-需求分析.md` 的 frontmatter 提供。缺少 `build` 会导致该方案开发失败。

### 编写要求

- 方案编号与日期一旦确定不要修改；需求变更时更新对应文件，并在文末追加变更记录。
- 方案内容必须能指导开发：接口写清方法/路径/参数/返回/错误码，数据模型写清表名/字段/索引。
- 涉及权限、安全、数据迁移、兼容性的改动必须单独成节说明。
- 引用其他文档使用仓库内相对路径，禁止写本机绝对路径。
