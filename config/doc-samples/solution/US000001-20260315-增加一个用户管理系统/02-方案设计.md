# 02 方案设计

## 总体架构

- 前端：用户管理页面，按权限渲染操作入口。
- 服务端：用户服务提供 REST 接口，统一权限中间件校验。
- 存储：用户表、角色表、权限表、用户角色关联表、审计表。

## 数据模型

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| user | id, tenant_id, username, status, deleted_at | 用户主表，软删除 |
| role | id, tenant_id, name | 角色 |
| permission | id, code | 权限，格式「资源:动作」 |
| user_role | user_id, role_id | 用户角色关联 |
| audit_log | id, actor_id, action, target, result, created_at | 审计日志 |

## 接口设计

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | /api/users | user:read | 分页查询用户 |
| POST | /api/users | user:create | 新增用户 |
| PATCH | /api/users/:id | user:update | 修改用户 |
| DELETE | /api/users/:id | user:delete | 软删除用户 |
| POST | /api/users/:id/roles | user:grant | 分配角色 |

## 权限设计

- 服务端统一校验「资源:动作」。
- 前端隐藏按钮只做体验优化，不作为安全边界。
- 超级管理员判断单独放行，并记录审计日志。

## 异常处理

- 用户名重复返回 409。
- 无权限返回 403。
- 用户不存在返回 404。

## 风险与取舍

- 软删除会增加查询过滤成本，通过索引与默认条件控制。
- 角色叠加可能导致权限过大，定期审计角色权限。
